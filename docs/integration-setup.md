현재 실행 중인 서버는 `artifacts/demo-2026-09-14/todo-checker-demo-server-windows-x64/todo-checker-demo-server`에 압축 해제한 배포본이다. 이 폴더의 `.env`에도 Google·OpenAI 설정을 적용했다. 해당 서버의 기존 `data/`와 서버 토큰은 유지했다. 지금은 별도 서버를 추가로 시작하지 않고 PC 앱에서 Google 계정 연결을 진행한다. 이후 직접 시작할 때는 이 폴더의 `start-server.cmd`를 사용한다. 배포용 ZIP 원본에는 실제 키를 넣지 않았다.

권장 순서: 앱 설치 → Google·Notion·iCloud 사이트 설정 → 서버 실행 → 앱 동기화 주소·토큰 입력 → PC 앱에서 계정 연결 → 조직별 위치 설정 → 양방향 동기화 확인.

iPhone 등록 중 `iTunes service key is empty`가 나오면 [Apple 로그인 준비 오류 해결 절차](accounts-and-installers.md#apple-로그인-준비-오류-itunes-service-key-is-empty)를 참고한다. `mobile`에서 `npm run apple:register`로 현재 Apple 설정 조회 오류를 우회하도록 준비했다.

앱과 서버 코드는 구현되어 있다. 실제 계정의 데이터 조회·생성은 아래 자격 증명을 설정한 뒤 확인해야 한다. 키나 암호를 채팅으로 전달할 필요는 없다.

## 1. 내 PC에서 서버 실행

Node.js 22.13 이상이 필요하다. 별도 DB 서버는 사용하지 않는다. 서버 데이터는 `server/data/state.sqlite`, 계정 암호화 키는 `server/data/credentials.key`에 저장된다. 데스크톱의 로컬 JSON과 휴대폰의 AsyncStorage도 계속 사용한다.

```powershell
cd server
npm ci
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
# .env를 편집한 다음
npm start
```

이미 `.env`가 있으면 복사 대신 기존 파일을 편집한다. 서버를 처음 실행하면 `data/token.txt`에 개인용 서버 토큰이 만들어진다. `.env`의 `SYNC_TOKEN`을 직접 지정해도 된다.

데스크톱 설정의 동기화 주소는 `http://127.0.0.1:8787`, 토큰은 위 파일의 값이다. 휴대폰에는 같은 Wi-Fi의 PC IPv4 주소(예: `http://192.168.0.10:8787`)와 같은 토큰을 입력한다. 휴대폰에서 `localhost`는 휴대폰 자신을 뜻한다. Windows 방화벽이 물으면 개인 네트워크의 Node 서버 접근을 허용한다.

PC와 서버가 켜져 있어야 외부 도구와 동기화된다. 서버 없이도 로컬 할 일 편집은 가능하며, 연결되면 동기화된다. 집 밖에서 사용할 때는 PC에 접근 가능한 HTTPS 주소가 별도로 필요하다.

## 2. Google 개발자 사이트

OAuth를 만드는 Google 계정과 실제 데모 캘린더 계정은 달라도 된다. 프로젝트의 테스트 사용자 목록에 데모 캘린더 계정을 추가하고, 앱의 Google 연결 화면에서는 그 캘린더 계정으로 로그인한다. [계정별 상세 절차](accounts-and-installers.md)를 참고한다.

현재 OAuth 앱은 사용자 확인에 따라 프로덕션 상태를 유지한다. 테스트 사용자 추가는 Testing 상태에서의 절차다. 프로덕션 게시 상태만으로 Calendar API 활성화·요청한 캘린더 권한 승인까지 확인되는 것은 아니므로 실제 연결과 목록 조회로 확인한다.

1. [Google Cloud Console](https://console.cloud.google.com/)에서 프로젝트를 만들거나 선택한다.
2. API 라이브러리에서 **Google Calendar API**를 활성화한다.
3. Google Auth Platform에서 앱 이름·지원 이메일·대상 사용자를 설정한다. 테스트 상태로 사용할 경우 본인 Google 계정을 테스트 사용자로 추가한다.
4. OAuth 클라이언트 유형을 **웹 애플리케이션**으로 만든다. 인증 처리가 이 앱의 서버에서 실행되므로 기존 데스크톱 OAuth ID를 그대로 사용하지 않는다.
5. 승인된 리디렉션 URI에 `http://localhost:8787/oauth/google/callback`을 정확하게 추가한다.
6. 발급한 값을 `server/.env`의 `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`에 넣고 `PUBLIC_URL=http://localhost:8787`로 설정한다. 서버를 재시작한다.
7. **PC 앱 → 도구 연결 → Google Calendar → Google 계정 연결**에서 로그인한다. 캘린더 목록과 일정 읽기·쓰기 권한을 모두 허용한다.
8. 앱으로 돌아와 목록을 새로고침하고 계정의 **위치 선택**을 누른다. 실제 캘린더와 조직을 고른다.

OAuth 리디렉션 URI는 등록된 값과 일치해야 하며, localhost는 로컬 테스트에 사용할 수 있다. [Google 웹 서버 OAuth 문서](https://developers.google.com/identity/protocols/oauth2/web-server)

`PUBLIC_URL`이 localhost일 때 Google 인증은 PC에서 한다. 연결된 계정은 서버에 저장되므로 휴대폰에서도 같은 계정의 캘린더를 선택할 수 있다. 휴대폰에서 직접 OAuth 인증까지 하려면 PC에 도달하는 HTTPS 주소를 `PUBLIC_URL`로 설정하고, 그 주소의 `/oauth/google/callback`을 Google에 등록한다. 키 변경 뒤에는 서버를 재시작한다.

요청 범위: `openid`, `email`, `calendar.calendarlist.readonly`, `calendar.events`. 권한이 없는 공유 캘린더는 가져오기만 가능하다.

## 3. Notion 개발자 사이트

개인용으로 가장 간단한 경로는 내부 연결 토큰이다.

1. [Notion 연결 관리](https://www.notion.so/profile/integrations)에서 사용할 워크스페이스의 내부 연결을 만든다.
2. 콘텐츠 읽기·삽입·수정 권한을 설정하고 연결 토큰을 복사한다.
3. 사용할 Notion 데이터베이스의 `••• → 연결 추가`에서 방금 만든 연결을 추가한다. 공유하지 않은 데이터베이스는 API로 접근할 수 없다. [Notion 인증과 공유](https://developers.notion.com/guides/get-started/authorization)
4. 해당 데이터베이스에 **앱 ID**라는 텍스트 속성을 하나 만든다. 앱이 새로 만든 업무의 ID를 저장하여 네트워크 재시도 시 중복 생성을 피하는 용도다.
5. **앱 → 도구 연결 → Notion**에서 토큰을 입력하고 연결한다.
6. 워크스페이스의 위치를 선택하고 제목·날짜·메모·완료 상태·앱 ID 속성을 매핑한다. 메모와 앱 ID는 다른 텍스트 속성으로 지정한다. 완료 상태가 체크박스가 아니라 상태/선택 속성이면 미완료·완료 값을 각각 고른다.
7. 조직을 선택하고 원본 생성·수정 허용, AI 자동 분배를 설정한다.

내부적으로는 데이터베이스 아래 실제 데이터 소스 ID를 사용한다. 같은 데이터베이스에 여러 데이터 소스가 있으면 해당 항목을 선택한다. [Notion 데이터 소스](https://developers.notion.com/reference/data-source)

Notion OAuth도 구현되어 있다. 공개 연결을 만들 경우 `NOTION_CLIENT_ID`, `NOTION_CLIENT_SECRET`을 서버에 설정하고 `${PUBLIC_URL}/oauth/notion/callback`을 리디렉션 URI로 등록한다. 설정되면 **Notion 계정으로 연결** 버튼이 나타난다. 개인 사용에는 내부 연결 토큰만으로 충분하다.

### 조직마다 Notion을 여러 개 연결하기

업무마다 팀을 지정할 수 있고, 프로젝트에 속한 업무는 프로젝트의 팀을 따른다. 한 팀에 Notion 연결 계정/워크스페이스와 데이터베이스를 여러 개 등록할 수 있다. 예를 들어 회사 팀에는 회사 업무 DB와 고객사 업무 DB를, 개인 팀에는 개인 프로젝트 DB를 연결한다.

계정의 **위치 선택 → 데이터베이스 선택 → 조직 선택 → 저장하고 가져오기**를 위치마다 반복한다. 다른 워크스페이스는 해당 토큰 또는 OAuth로 계정을 추가한 뒤 같은 과정을 반복한다. PC와 모바일 모두 **연결을 볼 조직** 필터와 조직별 목록에서 계정, 데이터베이스, 업무 종류, 기본 목적지를 확인할 수 있다.

새 위치는 기본 목적지를 자동으로 바꾸지 않는다. 기본 목적지를 직접 켜면 같은 조직에서 겹치는 업무 종류의 기존 기본 설정을 대체한다. 자동 분배 후보는 지정된 조직에 연결된 위치로 제한되며, 업무에서 목적지를 직접 선택할 수도 있다. 동일 데이터 소스를 다른 계정으로 중복 연결하는 것은 차단한다. 서로 다른 조직에는 별도의 데이터 소스를 연결한다.

Notion 연결은 봇 ID로 구분하므로 같은 워크스페이스 안의 서로 다른 내부 연결도 별도로 보관한다. 기존 내부 토큰을 다시 입력하면 연결 ID와 데이터베이스 설정을 유지한다.

## 4. Apple 계정 사이트

1. [Apple 계정](https://account.apple.com/)에 로그인한다.
2. 이중 인증을 설정하고 **로그인 및 보안 → 앱 암호**에서 이 앱 전용 암호를 생성한다.
3. **앱 → 도구 연결 → Apple Calendar · iCloud**에서 Apple 계정 이메일과 앱 암호를 입력한다.
4. iCloud 캘린더와 조직을 선택하고 가져오기·쓰기·자동 분배를 설정한다.

앱 암호는 iCloud 캘린더 등에 접근하는 외부 앱에서 사용할 수 있으며 이중 인증이 필요하다. [Apple 앱 암호 안내](https://support.apple.com/en-us/102654)

이 구현은 서버의 iCloud CalDAV 연결이다. Apple 개발자 등록이나 유료 개발자 계정은 필요하지 않다. iPhone의 ‘나의 iPhone’ 로컬 캘린더, Apple Calendar에 표시되는 Google 계정은 이 경로의 대상이 아니다. Google 계정은 Google 연결을 사용한다. 앱 암호를 폐기하거나 계정 비밀번호를 변경해 연결이 끊기면 새 앱 암호로 재연결한다.

## 5. OpenAI API

1. [OpenAI API 대시보드](https://platform.openai.com/)에서 사용할 프로젝트와 API 사용 결제를 준비하고 API 키를 발급한다.
2. 서버 `.env`에 `OPENAI_API_KEY`를 저장한다. 기본 모델은 `gpt-4.1-mini`이며 `OPENAI_MODEL`로 변경할 수 있다.
3. 서버를 재시작하고 도구 연결 화면에서 **API 키 설정됨**을 확인한다. 이는 환경변수 존재 확인이며 실제 모델 접근·결제 확인은 첫 분류 요청에서 이루어진다.
4. 조직별 Notion 업무 위치와 캘린더 위치에서 **AI 자동 분배**와 수신할 업무 종류를 설정한다. Google·Apple을 모두 사용하는 경우 조직 기본 목적지를 지정한다.

서버는 Responses API와 구조화된 JSON 출력을 사용한다. 분류에 필요한 제목·메모·조직·후보 설정을 보내며 계정 토큰은 모델에 보내지 않는다. [OpenAI 구조화된 출력](https://developers.openai.com/api/docs/guides/structured-outputs)

### 표현이 다른 중복 업무와 개인 메모리

1. **도구 연결 → 중복 업무 · 개인 메모리**에서 유지할 업무를 선택한다.
2. **AI로 중복 후보 찾기**를 누르거나 같은 조직의 비교할 업무를 직접 선택한다. OpenAI 키 없이도 직접 병합할 수 있다. AI는 같은 주제만으로 판단하지 않고 날짜·시간·메모를 함께 비교하도록 요청한다.
3. 두 업무의 제목·날짜·메모를 확인하고 판단 이유를 적는다. **같은 업무로 병합**을 누르면 선택한 첫 업무의 내용을 유지한다. 자동으로 내용을 재작성하지 않는다.
4. 원본의 서로 다른 제목·메모·일정, 계정/데이터 소스/원본 ID, 조직, 병합 관계와 사용자 판단 이유·시간이 서버의 로컬 SQLite 개인 메모리에 저장된다. **저장된 개인 메모리**에서 펼쳐 확인할 수 있다. 이는 앱의 개인 기록이며 ChatGPT 메모리나 모델 파인튜닝이 아니다.
5. **다른 업무로 기억**을 선택하면 내용이 그대로인 같은 쌍은 다시 후보로 제안하지 않는다. 날짜나 내용이 달라지면 다시 비교할 수 있다.

병합 자체로 외부 원본을 삭제하거나 문구를 덮어쓰지 않는다. 앱에서 병합된 업무를 이후 수정하면 연결된 쓰기 가능한 원본들에 반영한다. 원본별 이름과 상태는 업무 상세에서 볼 수 있고, 충돌 해결과 삭제도 원본을 선택해 수행한다. 반복 iCloud 일정의 수정 제한은 그대로 적용된다.

같은 원본을 다시 가져오면 기록된 원본 ID와 병합 관계로 기존 업무에 연결한다. 병합된 과거 업무 ID는 기기 동기화로 되살아나지 않는다. 다른 기기에서 과거 업무에 추가로 수정한 내용은 유지할 업무의 충돌 항목으로 남겨 확인할 수 있다. 전송 중이거나 생성 결과가 불확실한 업무는 전송 결과 확인 후 병합한다.

새로운 ID나 새로운 표현이 같은 업무인지는 AI가 후보를 제시하고 사용자가 확인한다. 같은 조직에 개인 메모리가 있으면 새 앱 업무의 자동 역방향 생성 전에 중복 검사를 하고, 후보가 있으면 **확인 필요**로 멈춘다. 직접 목적지를 지정한 등록 요청은 사용자의 명시적 선택으로 처리한다.

AI 검사에는 같은 조직의 최근 개인 메모리 최대 30건과 비교 업무 30개씩을 전달한다. 수동 검사에서 **다음 업무들도 검사**로 이어서 확인할 수 있다. 저장된 내용은 온전히 보관하고 모델 입력의 긴 제목/메모는 각각 1,000/2,000자로 제한한다. 계정 토큰은 전달하지 않는다. AI 검사에는 추가 API 사용량이 발생하며, 실제 의미 판단 정확도는 사용하는 모델과 업무 내용에 따라 달라진다.

### 기본 동기화

- 조직을 지정하고 날짜가 있는 “고객 미팅”을 추가한다. 해당 조직의 기본 캘린더 한 곳에 생성되는지 확인한다.
- 시간이 없으면 종일 일정이 된다. 시작 시각만 있으면 연결 위치에서 설정한 기본 길이(기본 60분)를 적용한다.
- Notion에서 가져온 업무의 제목을 앱에서 수정하고 원래 페이지가 수정되는지 확인한다.
- 원본에서 바꾸면 **전체 가져오기 · 전송** 또는 5분 주기 수집으로 앱에 반영된다. 기기 간 동기화는 앱 실행 중 15초 주기다.
- API 오류는 연결 위치나 전송 작업에 표시된다. 다시 시도 버튼으로 복구할 수 있다. 결과 불명 Notion 생성은 조회로 존재를 확인하며 무조건 새 페이지를 만들지 않는다.

## 현재 범위와 주의할 동작

- 개인용 공유 토큰 하나를 사용하는 서버다. 다중 사용자 인증·조직별 접근 권한 서비스는 포함하지 않는다.
- 앱의 일반 삭제는 앱에서 숨기는 동작이다. 외부 원본까지 삭제하려면 할 일 상세의 **원본에서도 삭제**를 사용한다.
- 캘린더의 TODO 완료 체크는 앱에만 보관한다. 완료를 일정 삭제로 바꾸지 않는다.
- Google 반복 일정은 발생 건별로 읽고 수정한다. iCloud 반복 일정은 발생 건별로 가져오되 수정·삭제는 원본 앱에서 한다. 반복 규칙 편집과 참석자 초대 발송은 지원하지 않는다.
- 캘린더 목록 수집 범위는 과거 1년~미래 2년이다. 이미 연결한 항목은 범위를 벗어나도 원본 ID로 상태를 확인한다.
- 양쪽에서 변경되면 원본과 앱 중 유지할 내용을 선택한다. Notion은 조회 직후부터 수정 요청 사이에 생기는 원격 변경까지 원자적으로 잠그지는 못한다. 수정 시 바뀐 매핑 속성만 보낸다.
- 서버는 한 프로세스로 실행한다. 백업하려면 서버를 종료하고 `server/data` 폴더 전체를 복사한다. 암호화 키 파일을 잃으면 저장된 계정 인증 정보를 복원할 수 없다. 기존 `db.json`은 최초 SQLite 이관 뒤에도 원본 파일로 남는다.

## 개발 검증

```powershell
npm test --prefix server
npm run test:ui --prefix desktop
cd mobile
npx expo export --platform ios --output-dir dist-check
```

서버 테스트는 가짜 HTTP 응답과 임시 로컬 SQLite를 사용하며 실제 계정에 쓰지 않는다. UI 테스트는 별도 테스트 프로필을 사용한다. 실계정 OAuth·권한·생성 결과 검증은 사용자 계정을 연결한 후 필요하다.
